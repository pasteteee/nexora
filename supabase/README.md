## Данные и ограничения

Созданы все 11 таблиц приложения 1: `profiles`, `workspaces`, `workspace_members`, `canvases`, `elements`, `sources`, `source_chunks`, `publications`, `canvas_snapshots`, `ai_requests`, `workspace_invitations`.

У всех таблиц включен RLS. Для API явно выданы права на необходимые операции и изменяемые колонки. Анонимный клиент не получает доступ к исходным таблицам. В локальном `config.toml` автоматическая выдача доступа новым таблицам отключена.

Дополнения к рекомендуемой модели:

- `workspaces.deleted_at` задает момент мягкого удаления. Все дочерние записи, поиск и публикации сразу становятся недоступны. Владелец видит удаленное пространство для восстановления в течение 30 дней. После этого восстановление запрещено.
- `source_chunks.position` — номер фрагмента начиная с нуля, уникальный внутри источника. `canvases.position` задает порядок холстов; одинаковые позиции разрешены, дополнительная сортировка выполняется по `id`.
- `elements.group_id` ссылается на объект типа `group` того же холста. Циклы запрещены, удаление группы снимает группировку с дочерних объектов. Изменения групп сериализуются транзакционной advisory-блокировкой на холст.
- `workspace_id` продублирован у дочерних сущностей для проверки доступа. Составные внешние ключи не позволяют связать холст, элемент, источник, фрагмент, публикацию или снимок с другим пространством.
- Поля принадлежности, авторства и системные даты нельзя изменять клиентским UPDATE. Профиль автоматически создается триггером Supabase Auth, а членство владельца — триггером создания Workspace.
- Координаты и размеры используют `double precision`. Не допускаются NaN, бесконечность и неположительные размеры. Настраиваемые границы мировой области должен дополнительно проверять сервер редактора.
- `profiles.preferences_json` предназначен только для несекретных настроек интерфейса. Роли и права в нем не хранятся.

В `elements.type` включены девять типов объектов ТЗ и служебный тип `group`. Содержимое и стиль хранятся в JSONB. Позиция камеры может храниться в пользовательских настройках отдельно от мировых координат объектов.

## Права по ролям

Владелец и редактор могут создавать, изменять и удалять холсты, элементы, источники, публикации и снимки. Наблюдатель читает данные своего пространства. Только владелец изменяет параметры Workspace, приглашает и удаляет участников, меняет их роли, удаляет и восстанавливает пространство, передает владение.

Публикация разрешена владельцу и редактору согласно приложению 2 и критерию приемки 19. Снимки создаются как неизменяемые записи: для нового состояния создается новый снимок.

Фрагменты, векторы, статусы обработки источников и диагностические записи ИИ записывает только серверный worker с `service_role`. Пользователь читает собственную историю ИИ, если его текущая роль — владелец или редактор. Перед любым вызовом worker сервер обязан проверить текущего пользователя, членство и роль по матрице. Привилегированный ключ обходит RLS и должен находиться только на сервере.

Роли определяются по таблицам БД и `auth.uid()`, а не по редактируемому `user_metadata`. Служебные `SECURITY DEFINER` функции расположены в неэкспонируемой схеме `nexora_private`, имеют фиксированный пустой `search_path` и ограниченные EXECUTE-права. Они нужны для проверки членства без рекурсии RLS, триггеров и атомарных операций. Публичные RPC-обертки выполняются как `SECURITY INVOKER`. Схему `nexora_private` не следует включать в API schemas.

## Операции RPC

Вызывать от имени пользователя с его действующей сессией Supabase Auth:

- `soft_delete_workspace(p_workspace_id)` — мягкое удаление владельцем.
- `restore_workspace(p_workspace_id)` — восстановление владельцем до истечения 30 дней.
- `transfer_workspace_ownership(p_workspace_id, p_new_owner_id)` — передача владения существующему участнику; прежний владелец становится редактором.
- `create_workspace_invitation(p_workspace_id, p_email, p_role)` — приглашение с ролью `editor` или `viewer`; возвращает `invitation_id`, одноразовый `token` и `expires_at`.
- `accept_workspace_invitation(p_token)` — принятие текущим пользователем с подтвержденным совпадающим email.
- `revoke_workspace_invitation(p_invitation_id)` — отзыв владельцем.
- `match_source_chunks(p_workspace_id, p_embedding, p_limit)` — поиск в доступном пространстве, максимум пять результатов, косинусное сходство, затем `id` для одинаковых оценок.

Приглашения действуют 72 часа. В БД сохраняется SHA-256 хеш, исходный токен выдается только при создании. Доставка ссылки по email выполняется будущим серверным обработчиком. Нельзя повторно принять использованное, отозванное или просроченное приглашение либо пригласить существующего участника. Владелец читает список приглашений с явным набором колонок; `token_hash` и `select('*')` для этой таблицы клиенту недоступны. Прямой INSERT участников закрыт: прием приглашения добавляет участника атомарно.

Публичный `get_published_canvas(p_slug)` разрешен также роли `anon`. Он проверяет активную публикацию и состояние Workspace и возвращает ограниченное представление холста и объектов. Случайный slug содержит 192 бита энтропии. Исходные Sources, фрагменты, пути файлов, снимки, история ИИ и служебные поля не возвращаются. Оригиналы изображений и ссылки на источники этим RPC не публикуются; для изображения в публичном viewer нужен отдельный процесс подготовки безопасного публичного ресурса.

## Файлы и поиск

Bucket `nexora-sources` приватный. Путь файла: `<workspace UUID>/<source UUID>/<filename>`. Сначала регистрируется запись `sources`, затем выполняется загрузка через Storage API по ее `file_path`. Чтение доступно участникам, загрузка, замена и удаление — владельцу и редактору. Для upsert предусмотрены SELECT, INSERT и UPDATE политики.

Лимит bucket — 25 МиБ. Разрешены PDF, PPTX, TXT, Markdown, PNG и JPEG. Ограничение Storage можно менять в настройках bucket без изменения кода. Проверка содержимого файла, расширения и MIME на сервере остается задачей обработчика загрузки; заявленное клиентом поле `size` не заменяет фактическую проверку Storage.

`source_chunks.embedding` — `vector(1536)` с HNSW-индексом `vector_cosine_ops`. Размерность 1536 выбрана как стартовый контракт, поскольку ТЗ не фиксирует модель embeddings. Все векторы одного индекса должны создаваться одной моделью; смена модели или размерности требует миграции и повторной индексации. Нулевые векторы запрещены. HNSW выполняет приближенный поиск; одинаковые оценки сортируются по UUID для воспроизводимости.

## Локальный запуск и тесты

Команды выполняются из `Project NEXORA/nexora`. Нужны Node.js, npm и запущенный Docker. Проверенная версия CLI — `2.121.0`:

```sh
npx --yes supabase@2.121.0 start
npx --yes supabase@2.121.0 db reset --local
npx --yes supabase@2.121.0 test db --local
```

`db reset --local` пересоздает только локальную тестовую БД. Начальные данные не загружаются: seed отключен. Не подменяйте `--local` на `--linked` для команды reset.

Тест `tests/001_nexora_rls.test.sql` использует pgTAP, реальные роли `authenticated`, `anon`, `service_role` и JWT-настройки текущей сессии. Он создает независимые UUID и временных пользователей, проверяет разрешения и запреты и заканчивается ROLLBACK. Любая неуспешная проверка дополнительно вызывает SQL-ошибку для CI/MCP. В хранилище создаются только транзакционные тестовые метаданные, без загрузки файлов.

17 октября 2026 года этот тест исполнен через Supabase MCP на PostgreSQL проекта: **217 проверок, 0 ошибок**. Подтверждены критерии 17 и 24 на уровне БД. После тестов проверено отсутствие тестовых пользователей, рабочих пространств и Storage-записей. Локальный стек Docker здесь не запускался.

Security Advisor не нашел замечаний. В Performance Advisor устранены четыре замечания о внешних ключах без покрывающих индексов. Остались информационные сообщения [Unused Index](https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index): база пока не содержит рабочих данных, поэтому удалять предусмотренные ТЗ индексы по этой статистике не следует.

## Работа с удаленными миграциями и типами

Обе миграции уже применены к указанному проекту. Для последующих изменений CLI использует отдельную авторизацию, независимо от плагина:

```sh
npx --yes supabase@2.121.0 login
npx --yes supabase@2.121.0 link --project-ref gattldfwkbvkxodshzwb
npx --yes supabase@2.121.0 migration list --linked
npx --yes supabase@2.121.0 db push --linked --dry-run
```

После проверки списка новых миграций: `npx --yes supabase@2.121.0 db push --linked`. Примененные SQL-файлы не редактируются; изменения оформляются новой миграцией через `migration new <name>`.

Типы текущей схемы сгенерированы из удаленной БД в `lib/supabase/database.types.ts`. Обновление после следующих миграций:

```sh
npx --yes supabase@2.121.0 gen types typescript --linked --schema public > lib/supabase/database.types.ts
```
