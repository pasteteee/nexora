# Storage SMTP и окружения Nexora

Эта задача покрывает приватность исходных файлов и разделение переменных окружения, критерии 18 и 25 ТЗ. Bucket `nexora-sources` уже создан в Supabase. Для выбранного пользователем Gmail подготовлена конфигурация; фактическое подключение и проверка доставки ожидают адрес Gmail и пароль приложения.

## Окружения приложения

Node.js 22.18+ поддерживает используемые инфраструктурные тесты; проверка выполнялась на Node.js 24. Команды запускаются из `Project NEXORA/nexora`.

В `.env.example` находятся только шаблоны. В локальном `.env.local` уже записаны URL текущего проекта и его действующий publishable key. `.env.local` игнорируется Git. В браузер разрешено отправлять только:

- `NEXT_PUBLIC_SUPABASE_URL` — HTTPS origin проекта Supabase; для локального Docker допустим loopback HTTP URL.
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` — современный ключ `sb_publishable_...`, доступ ограничивается RLS. Secret и legacy `service_role` JWT здесь отвергаются.

Серверные переменные:

- `APP_URL` — origin приложения. Для разработки `http://localhost:3000`; для preview и production — адрес соответствующего развертывания с HTTPS.
- `SOURCE_SIGNED_URL_TTL_SECONDS` — время действия подписанной ссылки, по умолчанию 60 секунд, допустимо от 1 до 300.
- `SUPABASE_SECRET_KEY` — необязательный `sb_secret_...` для будущих фоновых worker. Обычная выдача файлов его не использует. Хранить только в серверном secret store, не добавлять в `NEXT_PUBLIC_*` или `next.config.env`.

Модули `lib/env/server.ts` и `lib/storage/source-download.ts` защищены `import "server-only"`. Next.js остановит сборку при их импорте в клиентский компонент. `lib/env/public.ts` читает только две публичные переменные. Проверка в `next.config.ts` блокирует новые `NEXT_PUBLIC_*` переменные, пока их явно не добавят в разрешенный список.

Для preview и production создавайте отдельные наборы переменных на хостинге. `NEXT_PUBLIC_*` фиксируются во время сборки: после изменения URL или publishable key нужна новая сборка. При подключении другого Supabase-проекта сначала примените к нему миграции. Для каждой среды задайте соответствующий Site URL и точные Redirect URLs в Supabase Auth; список URL не изменялся автоматически без адреса развертывания.

## Приватные источники

Bucket `nexora-sources` имеет `public=false`, лимит 25 МиБ и MIME allowlist PDF, PPTX, TXT, Markdown, PNG, JPEG. Участник читает файлы только в доступном активном Workspace; загрузка, замена и удаление разрешены владельцу/редактору. Путь: `<workspace UUID>/<source UUID>/<filename>`. Запись `sources` создается до загрузки файла.

`GET /api/sources/:sourceId/download` принимает пользовательский access token в заголовке `Authorization: Bearer <access token>`. Сервер проверяет токен через Supabase Auth, находит источник с RLS и только затем создает подписанную ссылку. Используется publishable key и JWT текущего пользователя, без административного обхода политик.

Ответ содержит только `signedUrl` и `expiresIn`. Заголовок `Cache-Control: private, no-store` исключает общее кеширование. Отсутствие сессии дает 401, недоступный источник — одинаковый 404 для отсутствующего или чужого объекта. Ошибки SDK, переменные окружения и ключи не возвращаются клиенту. Ссылка является временным правом доступа: не следует логировать ее; уже выданная ссылка действует до истечения TTL.

Серверная выдача сейчас поддерживает Bearer-сессию. Подключение cookie-сессии к будущему интерфейсу входа — отдельная задача. Автоматический `getPublicUrl()` для Sources использовать нельзя.

## Подготовка Gmail

Используются `smtp.gmail.com`, порт 587, STARTTLS. В Google нужно включить двухэтапную аутентификацию и создать [пароль приложения](https://support.google.com/accounts/answer/185833?hl=ru). Это отдельный 16-символьный пароль, а не обычный пароль аккаунта. В некоторых рабочих/учебных аккаунтах создание паролей приложений ограничено администратором.

Шаблон `.env.smtp.example` можно хранить в Git. Рабочий `.env.smtp.local` уже создан с Gmail host/port и пустыми секретами; он игнорируется Git и не загружается Next.js. Заполните его локально:

- `SUPABASE_PROJECT_REF` — ref целевого окружения; сейчас `gattldfwkbvkxodshzwb`.
- `SUPABASE_ACCESS_TOKEN` — личный токен Management API из [настроек Supabase](https://supabase.com/dashboard/account/tokens). Он нужен только операционному скрипту, не приложению. Авторизация плагина не передает этот токен локальным скриптам.
- `SMTP_HOST` — `smtp.gmail.com`.
- `SMTP_PORT` — `587`.
- `SMTP_USER` — полный адрес Gmail.
- `SMTP_PASS` — пароль приложения Google без разделяющих пробелов.
- `SMTP_FROM_EMAIL` — тот же адрес Gmail; произвольный чужой адрес запрещен.
- `SMTP_FROM_NAME` — `Nexora`.
- `SMTP_TEST_TO` — один принадлежащий вам адрес для явно разрешенного проверочного письма.

Значения ключей и паролей в чат или в коммиты не добавляются. Внешний SMTP применяется к Supabase Auth через [Management API](https://supabase.com/docs/guides/auth/auth-smtp); одни только переменные Next.js не меняют почтовую конфигурацию Supabase.

После заполнения:

```sh
npm run smtp:configure
npm run smtp:check
npm run smtp:test
```

`smtp:configure` сначала проверяет TLS и авторизацию у Gmail, затем сохраняет SMTP-настройки в Supabase и перечитывает их. Обязательное подтверждение email выключается (`mailer_autoconfirm=true`), защита смены адреса остаётся включённой. Другие настройки Auth и URL не перезаписываются. `smtp:check` проверяет соединение и совпадение настроек, без отправки писем.

`smtp:test` отправляет ровно одно техническое письмо на `SMTP_TEST_TO` только при явном запуске команды. Паролей и ссылок для входа в письме нет. Успешное принятие письма SMTP-сервером не доказывает доставку во входящие: нужно подтвердить получение, проверив также папку «Спам». Этот тест проверяет тот же Gmail транспорт и сохраненную конфигурацию, но не инициирует регистрацию или сброс пароля пользователя Supabase. Полный email-процесс Auth дополнительно проверяется при реализации интерфейса регистрации.

Без Management API токена те же значения можно внести через [Supabase Auth → SMTP](https://supabase.com/dashboard/project/gattldfwkbvkxodshzwb/auth/smtp). Тогда для автоматического чтения конфигурации операционному скрипту по-прежнему потребуется токен. SMTP пока не применялся: реальные учетные данные еще не предоставлены, письма не отправлялись.

Локальный Supabase использует тестовый SMTP-перехватчик из `supabase/config.toml`; письма в локальном Docker не уходят в Gmail. Внешняя конфигурация задается отдельно для каждого облачного проекта. Данные SMTP хранятся в конфигурации Auth, а не в таблицах приложения или SQL-миграциях.

## Проверки

```sh
npm run test:infra
npm run lint
npm run build
npm run check:client-secrets
```

Тесты проверяют разрешенный набор публичных переменных, отклонение приватных ключей, отсутствие значений в ошибках, HTTPS origin, ограничения TTL, SMTP payload/readback и защиту адресов от подстановки дополнительных заголовков/получателей. Сканер проверяет `.next/static` и публичные HTML/RSC-артефакты на известные секреты, современные secret keys и `service_role` JWT, не печатая их значения. Сканер не заменяет проверку будущих обработчиков, которые сами могли бы сериализовать приватные данные.

Ранее выполненные 217 проверок RLS доступны в `supabase/tests/001_nexora_rls.test.sql`. Они дополнительно проверяют закрытое хранилище, ограничения по Workspace и отсутствие анонимного доступа. Данные и пользователи этих проверок откатываются транзакцией.

При проверке зависимостей исходной заготовки обнаружены advisories для Next.js 16.2.4. Next.js и eslint-config-next обновлены до 16.4.2, транзитивный source-map-js обновлен в пределах совместимого диапазона; изменения зафиксированы в lockfile. Повторный `npm audit --omit=dev` не нашел уязвимостей рабочих зависимостей. Общий `npm audit` по-прежнему сообщает о зависимостях инструментов разработки; их принудительное обновление за рамками задачи не выполнялось.

Проверены 13 инфраструктурных тестов, TypeScript, ESLint, production-сборка и публичные артефакты с контрольными серверными значениями. HTTP-проверка подтвердила 401 без сессии/с неверным токеном и 400 для неправильного UUID, `no-store` и отсутствие приватных значений в ответах. Дополнительно проверено, что запуск Next.js отклоняет публичную SMTP-переменную и service_role JWT вместо publishable key, не печатая значение. Полноценная загрузка и получение настоящего файла с реальной пользовательской сессией остаются интеграционным сценарием будущего интерфейса загрузки; текущая проверка разрешенного сценария подписания использует подмененный SDK, а RLS отдельно проверен в настоящей БД.
