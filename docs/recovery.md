# Восстановление после сбоев

Порядок при любом инциденте: **понять масштаб → остановить ущерб → восстановить → записать**.
Запись (что случилось, когда, что сделали) — комментарием в Trello-карточке или issue на GitHub.
SQL ниже выполняется в Supabase → SQL Editor от `postgres` (в обход RLS): сначала `select`, потом изменение.

## Быстрая диагностика

| Симптом у пользователей | Вероятная причина | Раздел |
|---|---|---|
| Сайт не открывается или 500 на всех страницах | неудачный релиз, сбой Vercel | [неудачный релиз](#неудачный-релиз) |
| Вход не работает, «Нет соединения», данные не грузятся | Supabase недоступен или неверные ключи | [Supabase недоступен](#supabase-недоступен) |
| «Нет связи» в редакторе, чужие правки не приходят | Realtime | [Realtime](#realtime-не-работает) |
| Ошибки помощника и поиска | ключ или лимит провайдера ИИ | [ИИ и обработка](#ии-и-обработка-материалов) |
| Материалы висят в «Индексируется…» | функция обработки остановлена | [ИИ и обработка](#ии-и-обработка-материалов) |
| Не приходят письма | SMTP | [почта](#почта) |
| Пропали данные | действие пользователя или сбой | [потеря данных](#потеря-данных) |

Статус платформ: [vercel-status.com](https://www.vercel-status.com), [status.supabase.com](https://status.supabase.com).

## Резервные копии

**Что копировать.** База (схема и данные) и файлы бакета `nexora-sources` — это **разные** копии:
бэкапы Supabase содержат базу, но не файлы Storage.

**База.** Проверьте в Supabase → Database → Backups, что доступно на вашем плане
(ежедневные копии на платных планах, PITR — отдельное дополнение). Дополнительно — ручной дамп
перед каждым релизом с миграциями:

```bash
npx --yes supabase@2.121.0 db dump --linked --role-only -f backup/roles.sql
npx --yes supabase@2.121.0 db dump --linked -f backup/schema.sql
npx --yes supabase@2.121.0 db dump --linked --data-only --use-copy -f backup/data.sql
```

Каталог `backup/` хранить вне репозитория и вне общих папок: в дампе персональные данные.

**Файлы.** Скопируйте бакет `nexora-sources` через Storage API или S3-совместимый доступ Supabase
(Storage → Settings → S3 Connection), например `aws s3 sync s3://nexora-sources ./backup/storage
--endpoint-url <S3 endpoint>`.

**Пользовательская копия.** Экспорт «JSON-копия страницы» — копия одной страницы у пользователя.
Импорта JSON в интерфейсе пока нет: вернуть страницу из JSON может только разработчик (вставкой
строк `canvases` / `elements`).

**Проверка копий.** Раз в месяц восстанавливайте последний дамп в отдельный проект Supabase или в
локальный PostgreSQL и открывайте на нём приложение. Непроверенная копия копией не считается.

## Неудачный релиз

1. **Откат кода.** Vercel → Deployments → последний рабочий Production-деплой → **Instant Rollback**
   (или Promote to Production). Это занимает секунды и не трогает базу.
2. **Миграции не откатываются.** Мы пишем их совместимыми со старым кодом, поэтому после отката
   кода база остаётся рабочей. Если миграция ошибочна — новая миграция-исправление, а не правка
   применённого файла.
3. Исправление идёт обычным путём: ветка `fix/…` → PR → CI → Preview → `main`.
4. Если проблема в переменных окружения: вернуть значение в Vercel → Redeploy.

**Сбой при `supabase db push`.** Каждая миграция выполняется в транзакции: упавшая не применяется
частично, предыдущие остаются. Прочитайте ошибку, исправьте файл **этой, ещё не применённой**
миграции, проверьте `bash scripts/db-test-local.sh`, повторите `db push --linked`.
Сверка состояния: `npx --yes supabase@2.121.0 migration list --linked`.

**Миграция повредила данные.** Остановить запись (откат кода на версию без проблемной функции), затем восстановление из бэкапа/PITR
или выборочный перенос строк из копии (ниже).

## Supabase недоступен

- Если упал сам Supabase — ждать по [status.supabase.com](https://status.supabase.com), пользователям
  сообщить. Данные в базе сохраняются.
- Редактор не теряет правки молча: индикатор не переходит в «Всё сохранено», переход на другую
  страницу блокируется. Пользователям — не закрывать вкладку до восстановления связи.
- Если упало только наше приложение: проверьте `NEXT_PUBLIC_SUPABASE_URL` и
  `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` в Vercel (не отозван ли ключ), затем Redeploy.
- Проект на паузе (Free-план после неактивности): Dashboard → Restore project.

## Realtime не работает

Правки при этом **сохраняются** в базу, только не приходят другим сразу. Пользователь видит
«Нет связи»; после переподключения страница и роль дозагружаются из БД.

Проверить: Supabase → Logs → Realtime; применена ли `20261108210000_nexora_realtime.sql`
(`migration list --linked`); есть ли политики на `realtime.messages`:
`select policyname from pg_policies where schemaname = 'realtime';`.
Превышение лимита соединений на плане — Reports / Usage.

## ИИ и обработка материалов

Редактор и автосохранение от ИИ не зависят: при любом сбое ИИ текст в безопасности.

| Что | Действие |
|---|---|
| Ключ провайдера отозван, кончились деньги | новый `AI_API_KEY` или другой `AI_PROVIDER` в Vercel → Redeploy |
| Провайдер недоступен | временно переключить `AI_PROVIDER` на другой (xai / anthropic / openai) |
| Сбой embeddings (Gemini) | новый `EMBEDDINGS_API_KEY` → Redeploy → материалы в `error` обработать заново |
| Пользователи упираются в лимит | поднять `AI_REQUESTS_PER_HOUR` → Redeploy |
| Обработка зависла в `processing` | повтор пользователем через 5 мин (захват через 310 с) или массово: |

```sql
update public.sources set status = 'pending', error_message = null
 where status = 'processing' and updated_at < now() - interval '10 minutes';
```

При сбое обработки оригинал файла и прежний индекс сохраняются: готовый индекс заменяется одной
транзакцией только после успешной обработки.

## Почта

- **Письма-приглашения** не уходят: приглашение всё равно создаётся, владелец видит ссылку и
  передаёт её сам. Проверить `SMTP_*` в Vercel, пароль приложения Gmail.
- **Письма Auth** (подтверждение, сброс пароля): `npm run smtp:check`. Если пароль приложения
  Gmail отозван — создать новый, `npm run smtp:configure`. Пока почта не работает, регистрация и вход
  продолжают работать (Confirm email выключен); не работают сброс пароля и подтверждение почты.
- Gmail упёрся в суточный лимит отправки — ждать сутки или перейти на почтовый сервис.

## Потеря данных

Сначала спросите, что именно и когда пропало.

| Что | Как вернуть |
|---|---|
| Блок, текст | Ctrl+Z в той же вкладке |
| Страница | «Корзина страниц» → «Вернуть» (30 дней) |
| Тетрадь | «Корзина» → «Восстановить» (30 дней, только владелец). Если кнопки нет — RPC от имени владельца ([admin-guide.md](admin-guide.md#тетради)) |
| Тетрадь удалена окончательно, материал удалён, данные испорчены | из бэкапа, ниже |
| Данные демо-режима | хранятся только в браузере, вернуть нельзя |

**Выборочное восстановление из бэкапа** (не откатывая всю базу):

1. Восстановить бэкап/PITR в **новый** проект Supabase (Database → Backups → Restore to new project)
   или дамп в локальный PostgreSQL.
2. Найти нужные строки: тетрадь в `workspaces`, её `workspace_members`, `canvases`, `elements`,
   `sources`, `source_chunks`, `publications`.
3. Выгрузить их (`copy ... to stdout` или `pg_dump --data-only -t ... --where`) и вставить в рабочую базу
   в порядке зависимостей: `workspaces` → `workspace_members` → `canvases` → `elements` → `sources` →
   `source_chunks`. Конфликты по `id` означают, что строка уже есть, — её не трогать.
4. Файлы материалов вернуть из копии бакета по тем же путям `<workspace>/<source>/<имя>`.
5. Владельцу — проверить тетрадь.

Полный откат базы на момент PITR затрагивает **всех** пользователей: только если повреждено
многое, с объявлением о потере изменений после выбранного момента.

## Утечка ключа

Сначала отозвать, потом разбираться.

| Ключ | Риск | Действие |
|---|---|---|
| `SUPABASE_SECRET_KEY` (`sb_secret_…`) | полный доступ к базе и файлам в обход RLS | Supabase → Settings → API Keys: создать новый secret key, удалить старый → Vercel → Redeploy. Проверить Logs на чужие запросы |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | низкий, он и так публичный, права ограничены RLS | заменить при злоупотреблении (нагрузка, спам-регистрации) |
| `AI_API_KEY`, `EMBEDDINGS_API_KEY` | траты на чужие запросы | отозвать в консоли провайдера, новый в Vercel → Redeploy |
| SMTP-пароль (пароль приложения Gmail) | рассылка от нашего имени | удалить пароль приложения в Google, создать новый, `npm run smtp:configure`, обновить `SMTP_PASS` в Vercel |
| `SUPABASE_ACCESS_TOKEN` | управление проектом Supabase | Account → Access Tokens → Revoke |
| Ключ попал в Git | история публична | отозвать ключ (удаление коммита не помогает), затем почистить историю при необходимости |

После любой утечки: `npm run check:client-secrets` и проверка, как ключ утёк.

## Злоупотребления

- Вредная публичная страница: `update public.publications set is_active = false where slug = '<slug>';`
- Спам-аккаунт: Authentication → Users → Ban user.
- Поток приглашений: ограничен 20 в час на тетрадь (аудит безопасности, PR #15); при необходимости
  забанить владельца.
